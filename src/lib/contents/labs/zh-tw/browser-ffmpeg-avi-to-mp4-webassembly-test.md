得到的結果既好笑又在技術層面上相當迷人：計時器停在了精準的 **747.44 秒**（差不多是 12.5 分鐘多一點），而以低溫聞名的 M3 晶片也讓鋁合金機身摸起來明顯發熱了。

那麼，為什麼一台配備了當今市面上最強大晶片之一的電腦，僅僅為了改變一部影片的格式，就需要「滿頭大汗」地跑上超過 12 分鐘呢？在本文中，我們將剖析這個過程背後的技術邏輯，並回答最終極的問題：*如果它這麼慢，為什麼我們還需要基於瀏覽器的處理工具？*

## 1. 第一個瓶頸：Remux 與 Transcode

這次測試花費這麼長時間的最大原因，其實不是機器的問題；而是原始檔案。我選擇的是一個較舊的 AVI 格式檔案，使用的是像是 DivX 或 Xvid 這類傳統的壓縮標準（Codecs）。

在影片處理的世界裡，你必須區分兩個核心概念：
*   **Remux（複製 - 速度極快）：** 如果你的來源影片已經使用了現代的 Codec（例如 H.264），FFmpeg 只要把影像和聲音的「核心」抽出來，然後塞進一個新的 MP4「外殼」裡就好。這個過程基本上就像是把資料從一個資料夾複製到另一個資料夾，只需要幾秒鐘的時間。
*   **Transcode（解碼與編碼 - 速度極慢）：** 因為我的 AVI 檔案使用了與 MP4 不相容的過時標準，FFmpeg 被迫「打掉重練」。它必須先將舊影片的每一個畫格（Frame）進行 **Decode（解碼）**，然後再把這一大堆畫格 **Encode（編碼）** 成現代的 H.264/H.265 標準。這種逐個像素運算的過程，非常消耗 CPU 效能。

## 2. 瀏覽器中 WebAssembly (WASM) 的現實面

為了在 Google Chrome 中直接執行像 FFmpeg 這樣重量級的軟體（原本是用 C/C++ 寫的），我必須使用 WebAssembly (WASM)。這對現代網頁來說是個奇蹟般的進步，但它有一個致命的缺點：**它無法完全利用專屬的硬體加速（Hardware Acceleration）。**

如果你在 Mac 上安裝原生的應用程式，像是 Handbrake 或 Premiere，軟體會直接呼叫硬體的 API（像是 Apple Silicon 上的 Media Engine）來加速算圖（Rendering）。這個過程快得驚人，還能讓機器保持涼爽。

然而，在 Chrome 的沙盒（Sandbox）環境中透過 WebAssembly 執行時，FFmpeg 會被隔離在這些硬體加速器之外。它被迫必須完全依賴 CPU 的純「肌肉力量」（軟體編碼 Software Encoding）來進行運算。儘管 M3 晶片性能強大，但在網頁環境中強迫 CPU 以 100% 的滿載狀態運作，速度永遠比不上專屬的硬體處理管線。

## 3. 為什麼 M3 MacBook Air 會發熱？

MacBook Air M3 採用了「無風扇（Fanless）」的設計。它在設計上非常聰明，能夠以卓越的效能處理爆發性的短期任務。但是，當我強迫它完全用 CPU 效能連續算圖 12 分鐘（持續性負載）時，累積的熱量就沒有風扇可以排出了。機器只能透過鋁合金機身被動散熱，最後甚至為了保護內部零件而開始降頻（Throttle）。

這其實也證明了一件事：基於瀏覽器的工具是貨真價實地在運用你機器的資源來做粗活，而不是只弄個假的進度條來騙你。

## 4. 那麼，這個工具的價值在哪裡？

你可能會問：*「既然這麼慢還會讓機器發熱，那為什麼不乾脆下載原生的軟體，或是傳到那些速度很快的線上轉檔網站就好？為什麼要用你的工具？」*

事實上，客戶端（Client-side）處理架構提供了其他解決方案無法取代的巨大價值：

*   **絕對的隱私與安全（零上傳）：** 當你使用線上轉檔網站時，你必須將影片上傳到他們的伺服器。你能保證他們轉檔完後會把檔案刪除嗎？使用我的工具，**100% 的處理過程都在你機器的記憶體（RAM）中進行**。沒有任何一個位元組的資料會透過網路傳輸出去。這是處理敏感的私人影片、公司內部資料或監視器畫面的完美解決方案。
*   **不受頻寬限制：** 想像一下你有一個 2GB 的影片檔。要把它上傳、等待伺服器轉檔、然後再把 2GB 的結果載下來，總共要花多少時間？如果你的網路速度很慢或是不穩定，在 Chrome 裡進行本地端（Local）處理絕對會更快且更可靠，就算實際算圖可能要花個 10 到 15 分鐘。
*   **方便且乾淨俐落：** 你是否正在使用公司電腦，或是借來的筆電，剛好又沒有管理員權限（Admin Rights）來安裝軟體？只要打開 Chrome，問題就解決了。
