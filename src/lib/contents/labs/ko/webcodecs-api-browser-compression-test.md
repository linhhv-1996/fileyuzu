웹 환경에서의 멀티미디어 처리는 빠르게 발전하고 있습니다. WebCodecs API와 웹어셈블리(WebAssembly, WASM)의 등장으로, 전용 하드웨어를 활용한 고강도 클라이언트 측 비디오 처리가 마침내 현실이 되었습니다.

하지만 이론과 실제는 다릅니다. 이 기술이 실제 환경에서는 어떻게 작동할까요? 이를 확인하기 위해 고강도 스트레스 테스트를 진행했습니다. 100% 브라우저 내에서 실행되는 맞춤형 비디오 압축 도구를 사용하여 300MB가 넘는 1080p 파일을 처리해 보았습니다. 그 결과, 최신 브라우저가 기기의 하드웨어와 어떻게 상호 작용하는지에 대한 매우 흥미로운 기술적 교훈을 얻을 수 있었습니다.

---

## 1. "실제 환경(Real-World)" 테스트 조건

모든 앱을 종료하고 RAM을 비우는 통제된 벤치마크 환경 대신, 우리가 매일 일하는 방식 그대로 테스트를 진행하기로 했습니다.

* **테스트 브라우저:** Chrome 버전 150.0.7871.187 (공식 빌드) (arm64).
* **테스트 기기:** MacBook Air M3, **16GB RAM** (팬리스).
* **멀티태스킹:** 브라우저에는 5~6개의 작업 탭이 열려 있었으며, 보조 모니터에서는 Firefox(Slack 실행 중)와 동시에 실행되었습니다.
* **입력 데이터:** Computerphile 채널의 매우 디테일한 학술 영상(*"How AI 'Understands' Images (CLIP)"*). 길이: 18분. 형식: MP4 1080p. 원본 크기: **327MB**.

이 테스트의 목적은 16GB의 통합 메모리(unified memory)가 멀티태스킹 작업으로 인해 심하게 공유되는 상황에서 WebCodecs API가 하드웨어 가속(Hardware Acceleration)을 얼마나 효과적이고 안정적으로 활용할 수 있는지 확인하는 것이었습니다.

---

## 2. 처리 단계: 하드웨어 가속의 위력

파일을 도구에 불러오고 처리를 시작하자마자 과정은 매우 매끄럽게 진행되었으며, 활성화된 다른 Chrome 탭에서 지연(lag)이나 끊김 현상이 전혀 발생하지 않았습니다.

이것이 바로 최신 포맷(MP4 등)에서 WebCodecs가 갖는 핵심 강점입니다. 브라우저를 쉽게 멈추게 할 수 있는 소프트웨어 기반 CPU 비디오 인코딩에 의존하는 대신, WebCodecs API는 컴퓨터의 전용 미디어 엔진(Media Engine)을 직접 호출하여 인코드/디코드 작업을 처리합니다.

팬리스 설계 때문에 처리 과정 내내 Mac M3의 하단 섀시 전체가 **상당히 뜨거워졌습니다**. 이는 하드웨어(특히 미디어 엔진)가 브라우저 환경과 하드웨어 가속기 사이에서 데이터 버퍼를 지속적으로 셔플하기 위해 한계까지 구동되고 있다는 명백한 물리적 증거입니다.

> **처리 아키텍처에 대한 기술적 참고 사항:** 도구의 성능을 최적화하기 위해 저는 듀얼 엔진(Dual-Engine) 처리 로직을 설계했습니다. 이번 테스트에 사용된 MP4 비디오의 경우, 시스템은 하드웨어 가속을 활용하기 위해 파이프라인을 WebCodecs로 자동 라우팅합니다. 하지만 WebCodecs가 지원하지 않는 레거시 포맷(예: `.avi`)을 업로드할 경우, 도구는 자동으로 폴백(Fallback) 메커니즘을 작동시켜 **순수 WebAssembly에서 실행되는 FFmpeg**로 매끄럽게 전환합니다. 이 FFmpeg 파이프라인이 활성화되면 CPU가 컴퓨팅 부하의 100%를 감당해야 합니다(소프트웨어 인코딩). 그 시점에서는 압축에 훨씬 더 긴 시간이 소요되며, 기기는 단순히 꽤 뜨거운 정도가 아니라 말 그대로 "불타는 듯이 뜨거워집니다(scorching hot)".

![The Limits of WebCodecs API in the Browser: A 350MB Video Compression Test](/lab_imgs/labs_001.jpg)

이번 MP4 테스트의 DevTools 콘솔 스크린샷을 살펴보면 다음과 같은 지표가 기록되었습니다.

| 지표 | 측정 결과 |
| --- | --- |
| **소요 시간** | 292.35초 (약 4.8분) |
| **원본 파일 크기** | 326.97 MB (327.0MB) |
| **목표 크기** | ~228.87 MB |
| **실제 출력 크기** | **352.85 MB** |
| **최적화 비율** | **-7.9% (파일 용량이 증가함!)** |

브라우저는 5분 미만의 시간 동안 끊임없이 작동하여 인코딩 작업을 완료했습니다. 하지만 가장 큰 반전은 출력 크기에 있습니다. 알고리즘은 228MB의 파일 크기를 목표로 했지만, 최종 출력 파일은 오히려 8% 가까이 부풀어 올랐습니다.

## 3. 기술적 분석: 파일 용량은 왜 커졌을까?

소프트웨어 엔지니어링 관점에서 볼 때, 이러한 "자폭"에 가까운 결과는 **비디오 압축은 마법이 아니라 수학**이라는 기본적인 원칙을 훌륭하게 입증해 줍니다.

이러한 파일 크기의 불일치는 두 가지 핵심 기술적 요인에서 비롯됩니다.

* **YouTube의 압도적인 압축 표준:** 입력 비디오는 YouTube에서 직접 다운로드한 것입니다. Google의 거대한 서버 인프라는 가장 복잡하고 진보된 인코딩 표준(VP9 또는 AV1 등)을 활용하여 단 1바이트까지 쥐어짜 냅니다. 원본 327MB 파일은 1080p 콘텐츠로서는 본질적으로 절대적인 최대 압축 한계에 도달한 상태였습니다.
* **재인코딩(Re-encoding)의 본질:** WebCodecs 도구가 작동할 때, 범용적인 기기 호환성을 보장하기 위해 강력하게 압축된 비디오 스트림을 디코딩한 다음, 이를 표준 H.264 형식으로 다시 패키징하고 재인코딩해야 합니다. 이미 촘촘하게 압축된 소스에서 동등한 시각적 품질을 유지하기 위해, 인코더는 YouTube의 고도로 최적화된 표준보다 더 높은 비트레이트(Bitrate)를 할당할 수밖에 없습니다. 그 필연적인 결과로 파일 크기가 비대해진 것입니다.

브라우저는 292초 동안 쉼 없이 연산을 수행하며 단 하나의 부인할 수 없는 사실을 증명했습니다. 수십억 달러 규모의 Google 서버에 의해 이미 극한으로 최적화된 파일을, 일반적인 브라우저 기반 인코더를 사용해 더 작게 줄일 수는 없다는 것입니다.

## 4. 결론: 브라우저 기반 압축의 진정한 활용 사례

이 테스트는 비교적 무거운 멀티미디어 파일을 브라우저 내에서 직접 안정적으로 처리하는 데 있어 WebCodecs API가 지닌 성숙도를 성공적으로 확인시켜 주었습니다. 하지만 동시에 이 기술의 한계 또한 명확하게 보여줍니다.

현실적으로, 브라우저 기반 비디오 압축 도구는 인터넷에서 추출한 비디오를 재압축하기 위해 만들어진 것이 아니며, **GB 단위의 원본 카메라 파일을 억지로 처리하기 위한 용도도 절대 아닙니다** (Premiere나 Handbrake 같은 전용 데스크톱 소프트웨어의 작업을 브라우저에 강요한다면 영원히 기다려야 할 수도 있습니다).

**이 도구의 진정한 힘과 완벽한 활용 사례는 바로 일상적인 파일 크기의 장벽을 즉각적으로 허무는 편리함에 있습니다.**

이것은 iPhone이나 Android에서 짧은 비디오를 막 촬영한 뒤 고객이나 파트너에게 즉시 보내야 하지만, WhatsApp, Line 또는 일반 이메일 클라이언트 같은 메시징 앱의 턱없이 작은 첨부 용량 제한에 막혔을 때를 위한 것입니다. 이러한 최적화되지 않은, 짧고 날 것 그대로인 비디오의 경우, 스마트한 듀얼 엔진 아키텍처가 순식간에 파일을 공유하기 안전한 크기로 압축해 줍니다.
